# 智驾仿真平台架构：面试可以这样画

## 1. 控制面、数据面、执行面

```text
                         控制面（Control Plane）
 ┌────────────────────────────────────────────────────────────────────┐
 │ 场景库 / 任务队列 / 调度器 / 资源配额 / 权限 / 配置 / 版本 / Dashboard │
 └───────────────────────────────┬────────────────────────────────────┘
                                 │ launch / cancel / retry
                                 ▼
                           执行面（Data Plane）
 ┌────────────────────────────────────────────────────────────────────┐
 │ Worker 1        Worker 2                  Worker N                  │
 │ Simulator       Simulator                 Simulator                 │
 │ + AD adapter    + AD adapter              + AD adapter              │
 │ + sensor        + sensor                  + sensor                  │
 │ + evaluator     + evaluator               + evaluator               │
 └───────┬──────────────────────────┬───────────────────────────┬─────┘
         │ artifacts                │ metrics                   │ events
         ▼                          ▼                           ▼
 ┌────────────────────────────────────────────────────────────────────┐
 │ 数据面：对象存储（log/video/point cloud）+ 元数据 DB + 指标时序库     │
 └────────────────────────────────────────────────────────────────────┘
```

- **控制面**只负责“跑什么、在哪跑、重试与治理”，不应在 API 请求线程内执行仿真。
- **执行面**负责进程隔离的具体仿真；一个 worker 失败不应拖垮其他任务。
- **数据面**保存可回放输入、输出和指标。大文件走对象存储，检索字段走数据库。

## 2. 单场景闭环执行器

```text
ScenarioSpec + AssetVersion + Seed
                │
                ▼
       Scene Builder / Map Loader
                │
                ▼
Time Coordinator ─┬─> Traffic / NPC / Weather
                  ├─> Physics / Vehicle Dynamics
                  ├─> Sensors (camera/lidar/radar)
                  └─> Ego State
                            │ observation @ t
                            ▼
                      AD System Adapter
                   perception→prediction→planning→control
                            │ action @ t + Δt
                            ▼
                      Actuator / Vehicle model
                            │
                            ▼
                Evaluator / Monitor / Recorder
```

**时钟协调器**是关键：各模块必须共享仿真时间、时间戳和 frame id。不能用系统墙钟时间替代 sim time；否则传感器、控制和评分会错位。

## 3. 核心接口（需要版本化）

```text
ScenarioSpec     = map + ego + agents + weather + events + seed
ObservationFrame = timestamp + frame_id + sensor payloads + ego state
Action           = timestamp + steering/throttle/brake 或 trajectory
MetricEvent      = scenario_id + time + name + value + evidence URI
RunManifest      = code/asset/model/config version + seed + platform version
```

选择 Protobuf/IDL/JSON 均可；关键是 schema 演进、单位、坐标系、nullable 规则和向后兼容。高频 payload（图像/点云）不应反复 JSON 序列化，可传 URI/shared memory/零拷贝句柄。

## 4. 扩展性与隔离

| 层 | 扩展方式 | 典型风险 | 防护 |
| --- | --- | --- | --- |
| 场景 | 参数化、组合、生成模型 | 组合爆炸、无效场景 | constraints、校验、覆盖率采样 |
| 执行 | 多进程/容器/GPU worker | 显存泄漏、进程挂死 | timeout、health check、资源回收 |
| 被测栈 | adapter/ABI/RPC | 版本不兼容、控制权冲突 | capability negotiation、contract test |
| 数据 | 分区/对象存储/索引 | 小文件爆炸、成本失控 | manifest、生命周期策略、采样 |
| 指标 | plugin evaluator | 指标定义漂移 | versioned metric、golden cases |

## 5. 架构设计题的回答顺序

1. 先问清 ODD、吞吐目标、被测对象、保真度和延迟要求。
2. 定义 scenario/observation/action/metric 四个契约。
3. 画控制面、执行面和数据面，说明失败隔离与资源调度。
4. 说明 replay、版本、seed 和 artifact 如何支撑定位。
5. 最后才谈具体引擎、消息队列、K8s 或数据库选型。

直接从“我会用 Kubernetes”开始，通常说明没有先澄清问题规模和边界。
