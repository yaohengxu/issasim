# 开环仿真与闭环仿真：作用、差别与评测

## 1. 最短定义

- **开环（open-loop）**：环境演化不受被测系统输出影响；通常复用记录的未来轨迹/传感器数据。被测系统可以输出动作，但动作不会改变下一帧世界。
- **闭环（closed-loop）**：被测系统输出的 action 会反馈给仿真世界，改变 ego 以及可能改变其他参与者的后续状态和传感器观测。

```text
开环
固定 log/scenario future ──> observation(t) ──> ADS ──> predicted action
       │                                                    │
       └──────────────── next observation(t+1) ◄────────────┘
                         （不使用 action）

闭环
world(t) ──> observation(t) ──> ADS ──> action(t)
   ▲                                             │
   └──── vehicle/traffic/physics transition ◄────┘
                  world(t+1) 再生成新观测
```

## 2. 差别的本质：是否存在反馈

开环可以回答“模型对历史数据预测得准不准”；闭环才可以回答“模型的输出会不会让车在未来撞车、偏航、闯灯，系统是否稳定”。

```text
Planner 在开环预测一条好轨迹
      │
      ├─ 不能证明执行后仍安全：真实动作会改变与周车的相对位置
      │
      ▼
闭环执行 action → 状态偏差累积 → 感知/预测再次变化 → 下一次决策
```

闭环更接近部署，但也更依赖传感器、车辆动力学、其他交通参与者反应和时间同步的可信度。

## 3. 开环仿真的作用

| 用途 | 为什么适合开环 | 常见指标 |
| --- | --- | --- |
| 感知离线回归 | 输入图像/点云和真值固定，可精准比较版本 | mAP、IoU、depth/pose error、latency |
| 预测模型评估 | 与真实未来轨迹直接对齐 | ADE、FDE、minADE、miss rate |
| 日志回放/调试 | 快、稳定、易复现，不需要全世界重建 | 复现率、处理耗时、差分输出 |
| 规划候选离线分析 | 可先检查可行性、舒适性、与专家轨迹差异 | route error、jerk、violation proxy |
| 数据挖掘 | 批量筛选 bad case / 覆盖分析成本低 | recall、ODD 分桶、失败聚类 |

开环优点是数据真实、标注可得、吞吐高、评估稳定；缺点是**不能评估交互后果**。例如规划器给出“提前向左避让”的动作，在日志回放里周车仍按原轨迹运动，无法知道该动作会不会诱发新的冲突。

## 4. 闭环仿真的作用

| 用途 | 为什么必须闭环 | 常见指标 |
| --- | --- | --- |
| 规划/控制验证 | action 影响位姿、轨迹和下一次输入 | collision、off-road、red-light、route completion |
| 安全关键场景 | 需要观察冲突如何随决策演化 | TTC、最小距离、near-miss、intervention |
| 交互/博弈 | ego 与 NPC 相互响应 | merge success、yield、deadlock、social compliance |
| 长时间稳定性 | 小误差会跨帧累积 | displacement、oscillation、jerk、stuck rate |
| RL / agent | 环境转移必须响应 action | return、success、safety constraint violations |

闭环并不自动“更正确”。若车辆动力学、NPC 行为或传感器延迟不可信，闭环的绝对分数也可能误导。正确用法是：明确其 ODD 和仿真保真边界，以真实数据/真机回放校准关键指标，并与开环回归结合使用。

## 5. 介于二者之间的形式

```text
日志背景 + 仿真 ego
  ego action 改变 ego 轨迹；背景车仍按日志走
  → 对 ego 是闭环，对交通交互是开环

反应式 NPC
  ego action 改变 ego；NPC 根据规则/模型响应
  → 更完整的多主体闭环

shadow mode
  真车/真实日志继续执行；ADS 只输出建议不接管
  → 用真实观测评估策略，不产生反事实物理结果
```

面试中应主动区分这些层级。不要将“ego 在仿真里能动”一概称为完整闭环，而要说明背景交通是否会对 ego action 响应。

## 6. 两者的时钟与接口区别

| 维度 | 开环 | 闭环 |
| --- | --- | --- |
| world source | recorded future / 固定回放 | simulation transition function |
| action 是否参与 transition | 否（或只记录） | 是 |
| 传感器观测 | 固定帧序列 | 由新世界状态渲染/生成 |
| timestamp | 匹配日志帧 | 由 sim clock 主导，需同步各模块 |
| 可复现 | 主要依赖数据/模型版本 | 还依赖 seed、physics、NPC、调度顺序 |
| 计算成本 | 相对低 | 相对高 |
| 典型被测模块 | 感知、预测、离线分析 | 规划、控制、端到端 agent、RL |

## 7. 评测设计：同一功能的两层门禁

```text
代码/模型改动
     │
     ▼
开环回归集
  ├─ 感知/预测是否退化？
  ├─ 是否保持历史场景的基本表现？
  └─ 快速、低成本、每次提交可跑
     │ pass
     ▼
闭环关键场景集
  ├─ action 是否引入碰撞、越界、闯灯、振荡？
  ├─ 交互/长时行为是否安全？
  └─ 成本高，作为 merge gate 或 nightly
     │ pass
     ▼
真实日志 / shadow / 真机验证
```

这就是平台为什么需要两者：开环提供高频、稳定的迭代信号；闭环暴露反馈和交互风险；真实验证检查仿真-现实差距。

## 8. 例子：前车急刹

```text
开环：
  输入固定的相机/雷达序列与前车真实急刹轨迹。
  评估感知是否检出前车、预测是否预测减速、规划输出是否合理。
  但无论 ego 输出刹车还是加速，下一帧仍是日志里的固定画面。

闭环：
  前车急刹事件在 t0 注入；ego planner 输出 brake。
  车辆模型推进 ego；相对距离、雷达回波、TTC 在下一帧变化。
  若 ego 刹车太晚/过猛/控制振荡，collision、jerk、最小距离会反映出来。
```

## 9. 常见误区

- “开环不算仿真”：错误。它是重要的回放/离线验证形态。
- “闭环分数一定比开环可信”：错误。闭环依赖环境和 agent 模型保真度。
- “闭环只要让 ego 运动就够”：错误。要说明周车、行人、传感器和时钟如何响应。
- “通过开环就能上线”：错误。规划控制的反馈风险需要闭环和真实验证。
- “闭环只看碰撞”：错误。还要看规则、舒适性、效率、鲁棒性与覆盖。

## 10. 面试 60 秒答案

> 开环仿真固定未来世界或日志帧，被测系统的输出不反馈到下一帧，因此适合高吞吐的感知、预测、日志回归和模型版本比较；它可以稳定地回答“对历史数据是否更准”。闭环仿真将规划/控制 action 输入车辆、交通和传感器状态转移，下一帧观测随 action 改变，才能评价碰撞、TTC、规则遵守、舒适性和长期稳定性。平台上我会把开环作为每次提交的快速回归门禁，把闭环作为关键场景和 nightly 评测，并记录 scenario、seed、资产/模型版本和事件日志以支持回放。对介于两者之间的日志背景+仿真 ego，我会明确它只对 ego 闭环、对交通交互仍是开环。

## 11. 深入理解：为什么不同模型更适合不同测试形态

### 11.1 先按“要验证的因果链”选择，而不是按模型名称选择

开环和闭环不是“感知模型只能开环、端到端模型只能闭环”的硬规则。正确的问题是：**这次测试是否需要验证模型输出对未来世界的后果？**

```text
只验证 input → output 是否正确？
    例如：图像中的车是否被检测到、预测轨迹是否贴近真实未来。
    → 开环优先：固定输入与真值，结果可精确对比。

还要验证 output → world transition → next input 是否安全？
    例如：刹车决策后是否避免碰撞、周车是否因 ego 并线而改变行为。
    → 闭环必需：action 必须影响后续世界和观测。
```

因此，同一个模型可同时接受两类测试：开环用于高频、低成本地定位输入输出退化；闭环用于验证其在反馈、误差累积和交互下的真实系统行为。

### 11.2 感知模型：开环是主评测，闭环是系统影响评测

感知模型的主要函数可以写成：

```text
f(image / lidar / radar at time t) → boxes / tracks / occupancy / lanes
```

它的标签通常来自已采集日志的人工或自动标注，因而可以把同一帧输入和同一份真值交给版本 A、B。这样才能保证 mAP 或 IoU 的变化主要来自模型，而非场景变化。

| 指标 | 含义 | 适合回答的问题 |
| --- | --- | --- |
| mAP | 不同召回点的 precision 平均值，常在指定 IoU/距离阈值下计算 | “车辆、行人等类别是否检得更准？” |
| IoU | 预测区域与真值区域的交并比 | “分割/占据/检测框的几何重合度如何？” |
| depth error | 预测深度和真值深度的绝对/相对误差 | “距离几何是否可信？” |
| pose error | 位置/朝向与真值的误差 | “目标位姿是否足以支持下游？” |
| latency | 从采样到可用输出的时间 | “模型能否在控制周期内给出结果？” |

感知也可以进入闭环：例如注入雨雾、掉帧或感知延迟后，观察 planner 是否急刹、是否撞车。这时测的不是纯 mAP，而是**感知误差对整车安全的传播影响**。所以平台通常先用开环锁定感知精度，再用闭环检查关键失败是否会造成系统风险。

### 11.3 预测模型：开环测“预测准确”，闭环测“交互预测是否有用”

预测模型常见接口是：

```text
history of agents/map → predicted distributions or trajectories for t+1...t+H
```

开环有记录的真实 future，可直接比较：

- **ADE (Average Displacement Error)**：预测轨迹与真实轨迹在所有预测时刻的平均位置距离；
- **FDE (Final Displacement Error)**：预测终点与真实终点的位置距离；
- **minADE / minFDE**：多模态预测的 K 条候选中，最接近真值的一条的误差；用于检查模型是否覆盖可能行为；
- **miss rate**：没有任何候选落入预设距离阈值内的比例。

这些指标适合检验“离线预测分布与日志未来是否相符”，但它们不保证规划使用该预测后仍安全。原因是：真实日志中的周车未来没有经历你的 ego action。若要验证“ego 提前并线，旁车会怎么让行/加速”，需要反应式 NPC 或行为世界模型，形成多主体闭环。

### 11.4 规划模型：开环做筛查，闭环决定是否可信

规划器可输出候选轨迹 `τ_ego`。开环可以检查：

```text
当前地图/障碍物/route
      │
      ▼
候选轨迹是否在可行驶区域、是否超过曲率/加速度限制、是否贴近专家轨迹
```

这适合快速发现明显违规、错误 route、过大 jerk 或无效轨迹。`violation proxy` 指基于当前或日志未来做的近似违规判断，例如候选轨迹是否穿过静态禁行区、是否明显越过当前红灯停止线。

但开环无法回答：执行轨迹之后，自车真实横摆/轮胎/制动响应如何？相对距离如何变化？旁车是否避让？感知输入是否因自车位姿变化而改变？因此规划的最终安全结论必须来自闭环；开环只应作为快速筛查和专家轨迹差异诊断。

### 11.5 控制模型：基本必须闭环

控制器的输入是目标轨迹与车辆状态，输出 steering / throttle / brake。它的正确性定义就是车辆动力学响应：

```text
control action(t) → vehicle dynamics → pose/speed(t+1) → next control input
```

没有这个反馈，控制器即使输出数值“看起来合理”，也无法知道是否过冲、振荡、制动力不足或延迟失稳。因此主要指标为：

- **tracking/displacement error**：实际车辆与参考轨迹的横向、纵向、航向误差；
- **oscillation**：方向/速度控制是否反复来回摆动；
- **jerk**：加速度变化率，衡量舒适性和控制平滑度；
- **stuck rate**：不应停却长时间低速/不前进的比例；
- **collision / off-road / red-light**：控制后果的安全/规则指标。

### 11.6 端到端模型：两类测试缺一不可，但闭环权重更高

端到端模型可能是 `sensor history + route → trajectory/control`。开环仍有价值：可以评估轨迹 L2、辅助 occupancy/detection head、推理延迟，以及某种天气/遮挡条件下是否明显退化；它非常适合作为每次代码提交的快速回归。

但端到端的动作会改变下一帧自己看到的画面和历史序列。一个很小的横向偏差就可能把模型带到训练日志里很少出现的状态（distribution shift），从而继续输出更差的动作。因此端到端的上线安全结论尤其要依赖闭环：扰动恢复、动作延迟、连续遮挡、反应式交通、长时稳定性与因果探针。

### 11.7 RL / 世界模型 / 多智能体：天然依赖闭环

- **RL** 的定义中环境转移 `s(t+1) = T(s(t), a(t))` 依赖 action；若 action 不改变环境，就无法学习/评估策略的 return。
- **世界模型**若用于预测“给定 ego action 后其他 agent 如何演化”，必须在闭环反事实任务中检查其因果合理性；只在日志未来上算 ADE 还不够。
- **多智能体**中 ego、NPC 都在影响彼此。固定日志背景只能测单边 replay，不能测 merge、yield、deadlock 等博弈结果。

## 12. 每项用途为何需要对应的指标

### 开环用途的细化

| 用途 | 固定什么 | 主要验证什么 | 为什么指标稳定 |
| --- | --- | --- | --- |
| 感知离线回归 | 传感器帧、标注、评测阈值 | 模型的识别/几何/延迟 | 输入与标签不变，版本差异可归因 |
| 预测模型评估 | 历史轨迹、真实 future、K 值 | 预测是否覆盖真实未来 | 真值 future 已记录，可直接算距离 |
| 日志回放/调试 | 原始消息、时间戳、配置 | 某 bug 是否能重复出现 | 没有随机世界分支，排查路径短 |
| 规划候选离线分析 | 当前 scene、route、约束 | 静态可行性、舒适性、专家差异 | 不需高成本重新渲染/交通演化 |
| 数据挖掘 | 海量日志与 ODD metadata | 哪类样本退化、是否覆盖长尾 | 可并行扫历史数据，吞吐高 |

其中：

- **复现率**：在同一数据/版本/配置下，某已知失败是否能被重新触发；不是“模型准确率”。
- **处理耗时**：每帧/每段日志的端到端处理时间，用于容量规划与性能回归。
- **差分输出**：同一输入下版本 A、B 的 boxes、occupancy、轨迹、告警的差异，用来解释指标变化。
- **ODD 分桶**：按昼夜、天气、路口、速度、遮挡、目标类型等切片指标；总体平均值可能掩盖关键退化。
- **失败聚类**：用标签、embedding 或规则将相似 bad case 聚合，避免人工逐条看海量日志。

### 闭环用途的细化

| 用途 | 必须让谁响应 | 主要评测什么 | 指标解释 |
| --- | --- | --- | --- |
| 规划/控制 | ego 车辆、传感器 | action 后果 | collision/off-road/red-light/完成率 |
| 安全关键场景 | ego + 事件物体，最好含交通响应 | 危险是否被化解 | TTC、最小距离、near-miss、接管 |
| 交互/博弈 | ego 与反应式 NPC | 协商/让行/并线 | merge success、yield、deadlock、合规性 |
| 长时间稳定性 | ego、传感器历史、动态世界 | 小偏差是否积累 | displacement、oscillation、jerk、stuck |
| RL/agent | 完整环境 transition | 策略是否优化任务而非投机 | return、success、约束违规 |

指标含义：

- **TTC (Time To Collision)**：按当前相对速度/轨迹估计的潜在碰撞时间；越小风险通常越高，但静态 TTC 不是完整碰撞预测。
- **near-miss**：未真正碰撞但最小间距、TTC 或危险区域指标低于阈值的险情；可发现“差一点撞到”。
- **intervention**：安全监控、人类接管或 fallback 被触发的次数/比例；需明确触发规则。
- **merge success / yield**：并线是否在限定距离、时间和安全间隙内完成；是否对有优先权的车辆合理让行。
- **deadlock**：多车互相等待或策略过度保守，超过阈值仍无有效进展。
- **social compliance**：对交通规则、礼让/间隙、舒适性等社会驾驶约束的合规度；必须在项目中明确定义，不能只用主观感受。

## 13. 工程落地：同一模型的双层评测矩阵

```text
                 PR / 每次提交                     nightly / release
感知             开环数据集 mAP、latency              闭环注入延迟/漏检后的系统风险
预测             开环 ADE/FDE、ODD 分桶               反应式 agent 与 ego 的交互安全
规划             开环 feasibility、route/jerk proxy    闭环碰撞、规则、效率、舒适性
控制             小范围轨迹跟踪回归                   闭环动力学、稳定性、极端工况
端到端           开环轨迹/辅助头/时延                 扰动恢复、长期闭环、因果探针
RL               policy/checkpoint 基础检查           return、安全约束、未见 ODD
```

最佳实践不是在两者中二选一，而是让开环提供快速、低噪声、可定位的工程反馈，让闭环验证输出后果和系统鲁棒性；再用真实日志、shadow mode 或真机测试校准两类仿真结果。

## 14. 感知为什么既要放进闭环，也不能只放进闭环

### 14.1 结论：全栈验证必须让感知在环（perception-in-the-loop）

对于真实部署的自动驾驶栈，正确的闭环链路应当是：

```text
world(t) / map / weather / agents
       │
       ▼ render / sensor simulation
camera / lidar / radar raw observations
       │
       ▼
perception → prediction → planning → control
       │                              │
       └──────────── action(t) ───────┘
                                      │
                                      ▼
                         vehicle + traffic transition
                                      │
                                      └──> world(t+1)
```

若闭环中把感知替换成完美真值（GT boxes、GT occupancy、GT tracks），测到的是“**oracle perception 条件下的规划控制能力**”，不是完整系统能力。它仍有价值，用于隔离规划/控制问题；但不能作为真实系统的最终安全结论。

### 14.2 为什么不能只依赖闭环评测感知

闭环确实能测“感知错误最后是否造成系统风险”，但无法高效、可靠地替代感知自身的开环回归。

#### 原因 A：无法清晰归因

```text
闭环发生碰撞
├─ 感知漏检？误检？距离/速度估错？
├─ 预测没有处理不确定性？
├─ planner 看到障碍却没有制动？
├─ controller/车辆动力学没有执行到位？
└─ NPC、传感器或 sim clock 的模型有误？
```

闭环最终只有“撞/没撞”等结果，定位成本高。开环固定传感器帧和标签，可立即知道某版模型在夜晚行人、远距离车辆或遮挡目标上是否退化；它是感知团队每次提交都能快速使用的单元/回归信号。

#### 原因 B：真实日志的真值不再与闭环分支对齐

开环日志中，时刻 `t+1` 的图像和标注来自真实车辆当时真实执行的轨迹。闭环中，若被测 planner 在 `t` 输出不同转向或制动，ego pose 已经改变，原日志的 `t+1` 图像/标注就不再是它会看到的世界。

```text
真实日志：ego 按人类轨迹走 → frame(t+1) 与 label(t+1)
闭环候选：ego 按 ADS action 走 → 应得到新的 frame'(t+1) 与 label'(t+1)
```

因此，闭环必须由可重新渲染/生成的世界提供新的传感器真值；不能把旧日志帧继续当作 action 后的观测。与此同时，想要做公平的 mAP/IoU 版本比较，固定日志仍是更干净的基准。

#### 原因 C：闭环结果可能掩盖感知退化，或夸大单点误差

- 某版检测 mAP 下降，但 planner 对冗余目标、occupancy 或雷达足够鲁棒，最终 collision 不变；这并不代表感知没有退化。
- 某次漏检触发碰撞，但真正原因可能是 planner 没有处理低置信目标；不能把所有责任归到感知。
- 模拟器中的感知错误模式与真实世界不同，闭环分数好也不等于真实安全。

所以系统安全指标和感知精度指标是互补的，不存在一个能完全代表另一个。

#### 原因 D：成本、吞吐和场景爆炸

全栈闭环需要每个物理步重新生成多相机图像、LiDAR、Radar，运行 DNN 推理，再让车辆/NPC 继续演化。它的成本通常远高于对已存日志离线跑一次感知。一个代码改动若只靠闭环才能发现 mAP 退化，反馈会慢、噪声高、GPU 成本也难以承受。

#### 原因 E：传感器保真度会成为新的混杂变量

感知在环时，结果同时受以下因素影响：

```text
模型版本
  + 渲染材质/光照/天气
  + camera 内外参、曝光、滚动快门、运动模糊
  + lidar/radar 噪声、遮挡、延迟
  + time synchronization、丢帧、buffer queue
  + ego/NPC 运动与地图语义
```

若这些传感器模型未校准，闭环测到的可能主要是 sim-to-real gap，而不是感知算法本身。开环真实日志基准能持续锚定模型面对真实传感器数据时的基本能力。

### 14.3 推荐：四种测试模式，而不是二选一

| 模式 | 感知输入 | 后续是否闭环 | 主要回答的问题 |
| --- | --- | --- | --- |
| 感知开环回归 | 固定真实日志 + 标注 | 否 | 模型精度、延迟、ODD 是否退化？ |
| Oracle-perception 闭环 | 仿真 GT / 完美结构化状态 | 是 | 规划控制、车辆/NPC/评测器是否正确？ |
| Perception-in-the-loop 闭环 | 仿真 raw sensor → 真正感知模型 | 是 | 感知错误在系统内造成什么安全后果？ |
| Shadow / 真车评估 | 真实 raw sensor → 真正感知模型 | 真实世界继续演化，模型不接管 | 仿真结论能否迁移、是否存在域差？ |

`Oracle-perception` 和 `Perception-in-the-loop` 应使用同一个 scenario、seed、action 时钟和 evaluator。二者安全指标的差值，是量化“当前感知误差给系统带来多少代价”的有力证据。

### 14.4 一个具体例子：夜晚遮挡行人

```text
1. Oracle-perception 闭环：
   GT 行人状态直接给 planner；若仍撞人，优先排查规划/控制/制动模型。

2. Perception-in-the-loop 闭环：
   相机模拟夜间曝光与遮挡 → 感知输出低置信/漏检 → planner 决策 → 车辆执行。
   若此时撞人而模式 1 不撞，说明感知或其不确定性接口是关键贡献因素。

3. 感知开环回归：
   在真实夜间遮挡日志上比较版本 A/B 的 recall、距离误差、latency，确认问题是否也在真实数据出现。
```

这种对照比只看一次闭环 collision 更能指导修复：可能是提高夜间 recall、把低置信目标传给 planner、优化制动安全 envelope，或校准仿真曝光/延迟。

### 14.5 平台实现要点

- SUT（被测系统）只能读取与真实部署一致的 raw sensor 和合法地图/route 信息；GT 只给 evaluator 或 oracle baseline，避免信息泄漏。
- 为每帧记录 `sensor_timestamp`、`perception_ready_timestamp`、`planning_timestamp`、`action_timestamp`，并在评测中模拟 queue、延迟、掉帧与过期数据。
- 将 sensor model、感知模型、planner、车辆模型、NPC policy、scenario 和 evaluator 全部写入 `RunManifest`。
- 每次 full-stack 闭环失败保存事件前后窗口的 raw sensor、perception output、action、world state 和视频，支持逐帧回放。
- 将固定真实日志开环集作为 release gate，将感知在环闭环关键场景作为 nightly/release gate；不要以任一单独指标决定上线。
