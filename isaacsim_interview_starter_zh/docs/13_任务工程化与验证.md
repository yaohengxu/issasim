# 任务工程化、测试与可复现性

## 1. 任务不是一段 while 循环

```text
Task Specification
  ├─ scene / asset version
  ├─ initial-state distribution
  ├─ observation + action contract
  ├─ reward / success / failure / timeout
  ├─ safety constraints
  └─ metrics + seed + expected baseline
              │
              ▼
      实现（scene builder + controller + evaluator）
              │
              ▼
    smoke test → deterministic regression → randomized evaluation → real validation
```

先写可测规格，再写 demo。比如“把球放入碗”应规定碗的坐标、球半径、允许水平误差、静止时间、超时、掉落定义，而不是只说“看起来放进去了”。

## 2. 成功条件应防止视觉作弊

```text
success =
  horizontal_distance(ball, bowl_center) < r_inside
  AND ball_height < rim_height
  AND ball_speed < stable_speed
  AND condition holds for N simulation steps
```

只检查终点帧会把飞过碗口的球误判为成功；只检查 controller `is_done()` 也不能证明物理任务成功。对于抓取，还应检查离桌高度、相对末端位姿持续性、夹爪状态和碰撞安全。

## 3. 指标分层

| 层级 | 指标例子 | 回答的问题 |
| --- | --- | --- |
| 物理 | 穿透数、接触冲量、稳定时间 | 仿真是否可信稳定？ |
| 控制 | tracking error、峰值速度、超限率 | 控制器是否可执行？ |
| 任务 | success rate、time-to-success、drop rate | 任务是否完成？ |
| 感知 | mAP、pose error、latency | 观测是否足够好？ |
| 系统 | reset/s、steps/s、GPU memory、crash rate | 是否能规模化？ |
| 迁移 | real success、sim-real gap | 是否真的可用？ |

输出均值时还应输出 trial 数、seed、置信区间或分位数；一次成功的录屏不是评估。

## 4. 推荐测试金字塔

```text
                  少量真机/高保真回放
               ─────────────────────────
             随机化 episode 评估（N seeds）
          ──────────────────────────────────
        固定 seed 的确定性任务回归（headless）
     ──────────────────────────────────────────
   单元测试：坐标变换、IK、reward、success predicate
─────────────────────────────────────────────────
```

- 单元测试不启动 GUI，验证纯函数；例如四元数/矩阵变换和 success 判定。
- smoke test 只检查场景能载入、机器人可读、能 step、无异常。
- 固定 seed 回归可发现资产路径、Prim 名称、参数变更带来的退化。
- 随机化评估是统计问题，要记录分布和失败类别。

## 5. 可复现实验最小清单

```text
Isaac Sim build/version
GPU driver + OS（若影响渲染/物理）
enabled extensions / renderer config
USD、资产 hash 或版本号
task config、randomization ranges、seed list
physics dt、solver、control frequency
policy checkpoint / controller gains
metrics schema + logs + video sampling rule
```

随机种子固定不等于跨 GPU/跨版本逐 bit 完全相同；面试时应诚实说明 determinism 的层级，并用容忍区间/统计回归而不是脆弱的单个浮点数断言。

## 6. 失败分类让迭代可行动

```text
失败 episode
├─ scene/asset：初始穿透、错误 collider、资产缺失
├─ perception：未检出、pose 偏、时序延迟
├─ planning：不可达、无碰路径失败、奇异
├─ control：超调、振荡、夹爪未闭合
├─ physics：滑落、反弹、约束不稳定
└─ evaluation：成功标签/时间窗口定义错误
```

每类失败保留 seed、任务参数、关键状态序列和短视频；只保留最终截图通常无法重放问题。

## 7. 性能工程

- 大规模训练优先 headless、限制 render 产品、复用资产与 wrapper。
- 避免每帧 USD 查询、字符串路径查找、频繁创建 Python 对象和逐环境 Python 循环。
- 将高频 state/action 用批量张量路径处理（具体接口取决于版本/框架）。
- profile 要分开看物理、渲染、Python、资产加载、数据写盘；不要把“FPS 低”笼统归咎于 GPU。

## 8. 面试官喜欢的交付结构

```text
project/
  assets/       USD 与来源/许可记录
  scenes/       可复现的场景层
  configs/      task、randomization、controller 参数
  src/          adapter、task、controller、evaluation
  tests/        unit + headless smoke/regression
  scripts/      train/eval/replay/export
  docs/         坐标系、接口、指标、已知限制
  runs/         不入库的大日志/视频，含 manifest
```

即使是 demo，也至少做到 `README + 一条命令运行 + 固定 seed + 成功条件 + 已知限制`。
